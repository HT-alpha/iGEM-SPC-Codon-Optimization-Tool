DNA Design Suite — full performance report (v2.9.4)

Standalone export of the 17 October 2026 measurement. The repository copy is docs/benchmarks/v2.9.4-full-performance-report.md.

Measured on 17 October 2026 against commit b8065f71d99f0cddc5968e3904b97d5f07b937e4 (PR #33, “Harsh performance suite, and a fix for rpoC assembly stalling”). Package version is 0.1.0. No tag was cut. Optimizer behaviour was left as that commit shipped it.

The machine-readable rows sit beside this file: DNA-Design-Suite-performance-rows-2026-10-17.json. An HTML rendering is DNA-Design-Suite-performance-report-2026-10-17.html.

Executive summary

On a release build (Cargo opt-level 3, thin LTO), CodonForge and PrimerForge match every published output pin from the v2.9.4 harsh suite: 76 rows, no pin failures, and the same CAI values, CDS hashes, primer pairs, ΔG values, operon joint costs, and the CAI-only GATE-BEN-001 claim of 50 of 50. The opt-level 1 build that earlier notes used returns those same outputs. Headline wall times on this 4-vCPU Xeon put the long path in seed repair. yeeJ (7077 nt) is 0.526 s with empty constraints (CAI 1), 2.727 s under the assembly rules (CAI 0.9727484991594185, of which seed repair is 1.764 s), 4.203 s under the tighter harsh set, and 4.012 s at budget standard with 4 generations, which does not change that assembly CDS. CAI plus structure on yeeJ is 3.458 s at the pinned vector [0.9723247970586831, 2.4166863375261896]. PrimerForge on the 7077 nt yeeJ template with 300 nt flanks is 0.052 s and returns the pinned pair TGACCGACAAATATTATG / GAACTACAGTGGTTTAAA, product 6843, ΔG −1.283850000000001. A single design stays near 53 MiB RSS. Three API designs serialized by Api.run_lock peak at 63112 KiB. waaS under the unpublished harsh constraint set still stops at CF-SRCH-006 in 0.059 s.

Method and commands to reproduce

From the repository root, after make setup and .venv/bin/pip install 'ViennaRNA==2.7.2'.

Opt-level 1, the profile the older notes use:

.venv/bin/maturin develop
.venv/bin/python tools/harsh_perf.py --suite all --out /tmp/cf-perf/opt1-harsh.json
.venv/bin/python tools/profile_suite.py --suite all --out /tmp/cf-perf/opt1-profiles.json
.venv/bin/python tools/challenging_perf.py --suite sweep --out /tmp/cf-perf/opt1-sweep.json
.venv/bin/python tools/challenging_perf.py --suite standard \
  --from /tmp/cf-perf/opt1-sweep.json --out /tmp/cf-perf/opt1-standard.json

Release, the headline profile:

.venv/bin/maturin develop --release
.venv/bin/python tools/harsh_perf.py --suite all --out /tmp/cf-perf/rel-harsh.json
.venv/bin/python tools/profile_suite.py --suite all --out /tmp/cf-perf/rel-profiles.json
.venv/bin/python tools/challenging_perf.py --suite sweep --out /tmp/cf-perf/rel-sweep.json
.venv/bin/python tools/challenging_perf.py --suite standard \
  --from /tmp/cf-perf/rel-sweep.json --out /tmp/cf-perf/rel-standard.json

harsh_perf.py --suite all is pins, design, seed, objectives, operon, primers, the API job path, and GATE-BEN-001. It exits 1 when any pin's ok is false. The timeout is 300 s per row. profile_suite.py is stage timings, seed counters, primer regions, structure, operon, cProfile, and Potts. challenging_perf.py is the v2.9.1 sweep (budget fast; structure jobs use 2 generations) and a standard rerun of the four slowest design jobs at 4 generations.

On this machine the release pass took 91 s (harsh), 37 s (profile), 26 s (sweep), and 14 s (standard). The opt-level 1 pass took 103 s, 44 s, 29 s, and 16 s. Every suite exited 0. No row timed out.

Sequences are the shipped validation FASTA files plus rpoB, rpoC, yfhM, thrA, and aceB read from benchmarks/corpus/NC_000913.3_cds.fna.gz. No sequence was invented. Assembly rules are benchmarks/validation/constraints_assembly.json. Golden Gate and BioBrick are examples/golden_gate.json and examples/biobrick_rfc10.json. The harsh set is that assembly file plus a 30 nt GC window in [0.35, 0.65], a homopolymer cap of 5, and a 10-mer cap of 2 (constraint_set_id cst_harsh_assembly). It is a stress set. It is not a published feasibility claim.

Bottlenecks, ranked

Ranked from the release counters on this machine. Inclusive times overlap, so the rank is by the outermost cost that a change would have to move.

  1. Seed repair on long, constrained CDS. yeeJ harsh seed 3.161 s of a 4.203 s design. climb is 2.072 s. Inside it, kmer_replace is 0.831 s (195161 calls) and ascend is 0.543 s. gc_delta is 0.174 s. is_feasible is 0.0014 s over 31228 calls, which is the v2.9.4 predicate change holding. The same order appears on ordinary yeeJ assembly (climb 1.035 s, ascend 0.358 s, kmer_replace 0.335 s) and on yfhM and rpoC, where kmer_replace and ascend are the two largest leaves. This is the same ranking the harsh note left in place.

  2. Tier 3 repair when generations are turned on. yeeJ assembly standard adds 1.485 s of tier 3 (repair 0.556 s) and keeps the generations-0 CDS. yfhM standard spends 1.722 s in tier 3 (repair 0.758 s) for the same outcome. The feasibility gate and the breed check are a few hundredths.

  3. Structure L0 folding, once structure is an objective. On yeeJ CAI + structure, tier 3 is 1.464 s beside a 1.646 s seed. l0_batch is 0.637 s and repair is 0.753 s. Fold traffic is 1 full fold, 18 local edits, 12 cache hits. rpoB structure is dominated by l0_batch (0.405 s) plus repair (0.344 s).

  4. ViennaRNA accessibility annotation on CAI-only fronts. 0.436 s of pfl_fold_up on the yeeJ assembly cProfile, after the search has finished. It is how the front reports a structure detail for a job that did not optimize structure. It does not run when structure is already an objective.

  5. GATE-BEN-001 as a batch. 5.985 s for 50 sequential CAI designs. That is the longest single row. It is fifty short jobs, not one slow gene. yeeJ alone at empty constraints is 0.526 s.

  6. Potts tier 2 is no longer the lacZ spike from v2.9.2. lacZ tier 2 is 0.153 s. yeeJ CAI + Potts still costs 1.638 s end to end, with only 0.43 s in the wrapped tier 1 and tier 2 calls. The rest sits in the front, including the annotation in item 4.

  7. PrimerForge is small next to seed repair. The slowest primer row is 0.080 s (yfhM, lengths 12–36, 13850 windows). Time goes to tm_prefilter, rank, and dimer, in that order on the wide pool. The 40-oligo cap still stops the survivor list at 1600. Raising it would change which pairs are scored. It was not raised.

  8. API serialization. Three accepts return in 0.006 s. The designs then run one at a time under Api.run_lock, and the row takes 0.958 s. Peak RSS is 62 MiB because one process holds the server and the jobs.

Honest limits

This run measured wall time, the harness phase counters, peak RSS, feasibility, CAI and objective vectors, and primer pair / ΔG pins, on one VM, one shot per row.

  • Rows are single launches. The yeeJ assembly fast wall on release spanned 2.371 s to 2.727 s across harnesses. There is no median and no instruction or cache-miss profile.
  • The published harsh, v2.9.3, and v2.9.2 numbers come from earlier runs that report the same CPU string. Cross-note wall ratios of a few percent are not a controlled A/B on one binary.
  • Release versus opt-level 1 is one rebuild of each profile, run back to back on this VM, with the machine otherwise quiet enough to finish, and still a shared KVM guest.
  • GATE-BEN-001 stays the CAI-only gate. LinearDesign, CDSfold, and DNA Chisel were not rerun. The v2.9.3 external comparison already records that boundary.
  • The harsh constraint set is a stress set. waaS failing it is a measured CF-SRCH-006, not a new feasibility theorem and not a defect against the assembly file.
  • Checkpoint resume, wheel cold-start, and the browser UI were not timed. The API row is in-process serve traffic for three jobs and one primer search.
  • Seed 7 is the published pin seed. The repair does not read the job seed; that was established in the search-escape note and was not re-swept here.
  • Genes are the shipped panel and validation FASTA set. Nothing was added to make a longer CDS.
  • The 40-oligo primer cap stayed at 40. A larger pool would change the ranked pairs and the ΔG that gets reported.
  • ViennaRNA was present (2.7.2). Structure rows need it. Without it those rows fail or skip, and this report would not have the structure vectors.
  • Package version stays 0.1.0. This document does not tag a release.
