`pattern_count` is called from `is_feasible` as well as from repair, which
is why the call count rose by about 448. The body is the ledger length.
rpoB `is_feasible` was 1.403 s over 956 calls and is 0.0001 s. rpoB prefix

waaS, and elastin-like.

The prefix tail still walks the suffix when the codon's GC count changes,
so most of the 25545 updates still touch the tail. What went away is the
serial rebuild of every entry, and the walk when the GC count is unchanged.
A range tree was not added: `gc_delta` is 0.027 s and stays an O(1) prefix
subtraction.

## Primer responses

`product_sequence` is built for the pairs that are emitted (at most 20),
not for every survivor. The returned JSON is the same bytes: all nine
primer SHA-256 values in the v2.9.2 rows match, including the 6477 nt
region at 166429 bytes and the 300 nt region at 44692 bytes. Those sizes
stay, because the twenty amplicons are part of the document. RSS for the
6477 nt row is 31564 KiB, next to 30720 KiB for the flank-50 row that
never scored 1600 long products. In v2.9.2 those two rows were 42468 KiB
and about 31000 KiB.

## What was not shipped

The non-dominated sort is still the specified `O(M N²)` walk. Replacing it
can move the primer bytes. It was left alone (0.021 s of the capped search).

The GC prefix is not a range tree. The tail delta is exact for the integer
counts and leaves 0.050 s on yeeJ, which is the suffix walk when a codon
changes the GC count.
