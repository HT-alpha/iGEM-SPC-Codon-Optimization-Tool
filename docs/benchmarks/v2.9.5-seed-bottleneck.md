# Seed repair bottleneck (v2.9.5)

Measured on 18 October 2026. The before column is commit `0e70d4b` (the tree that published `docs/benchmarks/v2.9.4-full-performance-report.md`). The after column is this change, built and run on the same machine the same day. Package version is 0.1.0. No tag was cut.

The v2.9.4 report put seed repair first on a release build: yeeJ harsh seed 3.161 s of a 4.203 s design, with `climb` 2.072 s and, inside the codon edit, `kmer_replace` 0.831 s (195161 calls), `ascend` 0.543 s, and `gc_delta` 0.174 s. The before column here is that same seed on this machine: yeeJ harsh 3.160 s, `kmer_replace` 195161 calls and 0.837 s. The ordering is the same on yeeJ assembly, yfhM, and rpoC.

## What was slow

Seed repair writes one codon at a time, then asks whether the sequence is still inside the GC windows, the k-mer caps, and the motif rules. On a long CDS that write was doing more work than the decision needed.

Replacing a codon rebuilt the k-mer counts from scratch for every window that overlaps the three new bases. Each window was packed by walking `k` bases and then inserted into a `HashMap`. Assembly uses a 12-mer cap of 1, and the harsh set adds a 10-mer cap of 2, so almost every word is unique. A single codon therefore inserted and deleted on the order of `k` keys. The standard library map in this toolchain also shrinks when keys are removed, and the next insert grows it again, so many edits rehashed the whole table. That is the `kmer_replace` counter: about 4 µs per call, 0.837 s on harsh yeeJ.

Finding the other copy of a repeat did the same kind of work at CDS scale. `hot_codons` packed the construct (0.035 s on harsh yeeJ, 20 calls) and the climb that consumes those sites was 2.070 s.

The CAI ascent tried every synonym of a position against every synonym of a partner. A pair that cannot raise CAI still wrote both codons, updated k-mers and GC, scored the geometric mean, and wrote the old codons back. `cai_of` is `exp` of the mean of one `ln` weight per counted codon. The ascent keeps a pair only when that value is strictly higher, and the feasibility check sits behind that comparison, so a losing pair never called `is_feasible`. It still paid for the two edits.

The GC penalty and the count of windows outside the band walked the same windows on every edit. That is real (`gc_delta` 0.175 s on harsh yeeJ) and smaller than the k-mer work. The GC sweeps still probe a codon without writing it, and that path was left as a probe.

## What changed

All of this is in `crates/cf-constraints/src/seed.rs`. The pinned sequences did not move. Edit counts, cycle counts, and `is_feasible` call counts did not move either. `kmer_replace` and `gc_delta` drop by the same number of calls, because each skipped ascent pair used to enter `set_codon`, and `set_codon` records both counters.

The k-mer book now stores the packed word for each window. A codon edit patches the two-bit lanes of the windows that overlap those three bases and updates one open-addressed table. The table is sized once from the window count and does not grow or shrink. A multiply mixes the low `2k` bits before the probe, so a packed word does not cluster in the first few buckets. A canonical rule still folds the reverse word at lookup. A base that is not ACGT still repacks the touched windows from the buffer.

Each word keeps a chain of the positions where it occurs. The climb follows that chain instead of packing the CDS. A window that starts past the last codon is not turned into a codon index. The pinned jobs have empty flanks, so that guard does not add or remove a site on them.

The ascent skips a pair when the sum of the two log-weight changes is at or below `-1e-6`, or when the pair would introduce a counted weight of 0 (the geometric mean becomes 0). Pairs closer than that, including an exact tie, still go through `cai_of`. A few thousand `ln` terms round by well under `1e-8`, and a one-codon step in the ribosomal table is about `0.006`, so a pair this far down cannot come back above the incumbent. That is why `is_feasible` stays at 31228 on harsh yeeJ while `kmer_replace` falls by 47252: the skipped pairs were the ones the CAI test already rejected before feasibility.

`set_codon` now updates the GC penalty and the offender count in one walk. `gc_delta` remains the virtual probe the sweeps use, which is why `gc_sweeps` barely moves (harsh yeeJ 0.1153 s to 0.1105 s on the release build).

Tier 3 repair, the pass that runs when generations are on, was not changed. The ViennaRNA `pfl_fold_up` annotation that the v2.9.4 report measured at about 0.436 s on yeeJ was not changed either. It still runs after search on a CAI-plus-structure job, and the API still returns that vector. Dropping it would remove a value the suite pins and a user-facing result, so it stays.

## Pins and what stayed

The four seed rows above match the v2.9.4 CDS hashes and CAI values, with the same edit and cycle counts. `tools/harsh_perf.py --suite seed` reported `pin_failures` empty on both profiles.

On the release build, `tools/harsh_perf.py --suite all` exited 0. That is 76 rows and an empty `pin_failures` list. yeeJ CAI plus structure is still `[0.9723247970586831, 2.4166863375261896]`, with 12 hits, 1 full fold, and 18 local edits. The 300 nt yeeJ flank primer document is still `5f1fa115bcefde58d0c3d92a35e7adbc5fcbf04bf78b6efe43bf75f946aa149f`. `GATE-BEN-001` is still 50 of 50, and no gene fell behind the stored CAI. The structure annotation was not removed or deferred.

## Tests

Two tests in `crates/cf-constraints/src/seed.rs` lock the new bookkeeping to the old answers.

`kmer_replace_matches_a_rebuild_and_does_not_rehash` edits a sequence that contains an `AAAACCCC` repeat and an `N` run, under a non-canonical 4-mer, a canonical 6-mer, and a non-canonical 8-mer. After each edit the stored words, the chains, and the excess match a book built from scratch. The bucket array length is the length reserved at build.

`codon_edits_keep_kmer_counts_gc_penalty_and_only_skip_losing_pairs` applies random codon edits on a solver with two GC windows and those k-mer rules. The penalty stays within `1e-8` of a full recompute, the offender counts match, and the bucket array does not change length. It then forces one alanine onto a light synonym and its neighbour onto weight 1. Every pair the filter rejects has `cai_of` at or below the incumbent, and at least one pair that raises CAI stays eligible.

`crates/cf-constraints/tests/seed_assembly.rs` still pins yeeJ assembly at the hash and CAI above.

Negative controls were injected, the test failed, and the edit was reverted:

- The window span started at `k - 2` instead of `k - 1`. `kmer_replace_matches_a_rebuild_and_does_not_rehash` failed on excess at the first edit.
- `shifts_can_raise_cai` returned false for every pair. `codon_edits_keep_kmer_counts_gc_penalty_and_only_skip_losing_pairs` failed because a rejected pair raised CAI from 0.290968458454092 to 0.2926806284941358.
- The fused GC update returned the penalty plus 1. The same test failed because the penalty had drifted by 1 on the first codon.
